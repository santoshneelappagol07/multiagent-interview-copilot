Question:
- Can you tell me what is memory management in Python?

Answer:
- Yes, basically in Python memory management means how Python allocates memory for objects, uses it, and then frees it when object is no longer needed.

**When it comes to allocation**
- Python creates objects in memory automatically when we assign variables, create lists, dictionaries, strings, like all these things.
- Here we as developer normally do not manage memory manually like in C or C++, Python runtime takes care of it.
- The main memory area used for Python objects is **heap memory**.

**Coming to cleanup**
- Python uses **reference counting** to track how many references are pointing to an object.
- When reference count becomes zero, object becomes eligible for cleanup, so memory can be released.
- For cyclic references, Python also has **garbage collector** to clean objects which reference each other and are no longer needed.

**One more thing**
- Python also has **memory manager** inside interpreter which handles private heap, object allocation, and reuse of memory blocks.
- So from developer side, we just need to avoid unnecessary object creation and keep references only when needed.
- In practice, if we use large data structures or long-running services, then memory usage should be monitored properly.

Question:
- What is **GIL** in Python?

Answer:
- **GIL** means **Global Interpreter Lock**. It is a lock in **CPython** which allows only one thread to execute Python bytecode at a time.

**When it comes to threading**
- So even if we create multiple threads, only one thread can run Python code at a time inside same process.
- This is mainly there to protect internal memory management and make object handling safe.
- Because of this, Python threads are not very useful for CPU-heavy work.

**Where it helps**
- For **I/O-bound** tasks like file handling, network calls, API requests, threads can still help because thread can wait during I/O.
- In that case, other threads can get chance to run while one thread is waiting.
- So for web apps or API calls, threading can still give benefit.

**For CPU-heavy work**
- If task is heavy computation, like data processing or number crunching, then **multiprocessing** is better than threading.
- Because multiprocessing uses separate processes, each process has its own Python interpreter and its own GIL.
- So real parallel execution is possible there.

**In short**
- GIL is a limitation for parallel CPU execution in Python, but it is useful for keeping interpreter internals safe.
- In my understanding, for backend services we normally use threads for I/O and processes for CPU-heavy jobs.

Question:
- Explain what **async** and **await** are in Python

Answer:
- Yes, basically **async** and **await** are used to write asynchronous code in Python, so we can handle I/O tasks without blocking the whole program.

**When it comes to async**
- We define a function with **async def** when that function may do waiting work like API call, database call, or file operation.
- This tells Python that function can pause and give control back to event loop.
- So it is useful when we want better concurrency for I/O-bound tasks.

**Coming to await**
- **await** is used inside async function to wait for another async operation to complete.
- While waiting, event loop can run other tasks, so program does not sit idle.
- This is the main reason async code can handle many requests efficiently.

**For example**
- In a FastAPI service, if one request is waiting for external API response, another request can still be processed by event loop.
- So here we use **async/await** to improve responsiveness in backend services.
- But if code is CPU-heavy, async will not help much, because it is mainly for waiting operations.

**In short**
- **async** defines asynchronous function, and **await** pauses that function until awaited task is done.
- So together they help in non-blocking execution, especially for network and database type operations.

- How would you debug a **memory leak** and check what is happening in memory?

Answer:
- Yes, first I will confirm whether memory is really increasing continuously, and then I will isolate which part of code or request flow is holding objects in memory.

**When it comes to first check**
- I will monitor process memory using server logs, container metrics, or system tools like **top** and **ps**.
- If memory keeps growing after same request pattern, then it is a strong sign of leak.
- In backend services, I also check whether garbage collection is not releasing objects because references are still alive.

**Coming to debugging approach**
- I will take **heap dump** or memory snapshot and compare object growth over time.
- Then I will look for repeated objects, large collections, cached data, or unclosed resources.
- In Python, I usually check for things like global lists, open file handles, DB sessions not closed, or large response objects kept in memory.

**What I check in code**
- I will inspect long-lived objects, background tasks, and caches, because these are common places where memory stays retained.
- I will also check circular references and event listeners if applicable.
- If issue is from third-party library or external call, I will isolate that path and test with smaller load.

**How I fix it**
- I remove unnecessary object retention, close resources properly, and use streaming or pagination for large data.
- If needed, I will add limits on cache size and clear unused data.
- After fix, I again monitor memory under same load to confirm it is stable.

**In my projects**
- In backend and AI services, this kind of issue can happen when response payloads or session data are kept too long.
- So I normally debug by observing memory trend first, then tracing object retention, and finally validating fix with repeated requests.
- That way I can find whether it is real leak or just normal memory growth.

Question:
- How would you write code to find continuous page ranges from a list of page numbers, and return single pages when sequence is broken?

Answer:
- Yes, I can do that by scanning sorted pages and grouping only continuous numbers into one range.

**When it comes to logic**
- If next page is exactly previous page plus **1**, then it is same sequence.
- If sequence breaks, I close current range and start new one.
- If only one page is there, I return it as single value, not as range.

**Coming to the code**
- I will first sort the pages, because input may not always come in order.
- Then I keep **start** and **end** pointer for current sequence.
- For output, I format continuous pages as `"2-4"` and single page as `"11"`.

**Example**
```python
def page_ranges(pages):
    pages = sorted(set(pages))  # remove duplicates and sort
    result = []

    start = end = pages[0]

    for page in pages[1:]:
        if page == end + 1:
            end = page
        else:
            result.append(f"{start}-{end}" if start != end else str(start))
            start = end = page

    result.append(f"{start}-{end}" if start != end else str(start))
    return result
```
