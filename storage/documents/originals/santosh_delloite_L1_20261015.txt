Question:
- Why can't the model be an attack vector?

Answer:
- Actually, model can become an attack vector if we do not control inputs and outputs properly, because LLM can be manipulated through prompt injection, unsafe data, or malicious content.

**When it comes to input risk**
- If user input is not sanitized, attacker can try to override system instructions or force model to reveal hidden context.
- So here the model itself is not the only issue, the real problem is untrusted input going into it.

**Coming to output risk**
- Model can generate harmful text, wrong instructions, or sensitive data if guardrails are weak.
- That is why we need **content filtering**, **policy checks**, and **response validation** before showing output.

**In terms of connected systems**
- If model is connected to tools, APIs, or databases, then bad prompt can make it call wrong action or expose data.
- So I always treat LLM like a powerful component, but not a trusted one by default.

**How I handle it**
- I use **least privilege**, strict **role separation**, and only allow approved actions through backend logic.
- Also I keep **logging**, **monitoring**, and manual review for sensitive flows, so any abnormal behaviour can be caught early.

- Why do you think model can be prone to security risk, and have you heard about prompt injection?

Answer:
- Yes, definitely. Model can be prone to security risk because it follows natural language instructions, so attacker can try to manipulate it using **prompt injection**.

**When it comes to prompt injection**
- Basically attacker puts hidden or misleading instruction inside user content, and model may treat that as a valid command.
- This is risky when model is reading emails, documents, web pages, or any external text.

**Why it happens**
- LLM does not understand trust boundary like traditional code, so it can mix system instruction with untrusted input.
- So if prompt design is weak, model may ignore original task and follow malicious instruction instead.

**What can go wrong**
- It can leak sensitive context, produce unsafe output, or trigger wrong tool action if model is connected to APIs.
- In my understanding, this is one of main reasons we should not trust model output blindly.

**How to reduce it**
- I would separate trusted instructions from untrusted content, use **input sanitization**, **output validation**, and strict **tool permission**.
- Also for sensitive use cases, I would add **policy checks** and keep model actions limited to approved workflow only.

Question:
- What is RAG, and when would you use RAG or not use RAG?

Answer:
- Yes, I have idea on **RAG**, means **Retrieval Augmented Generation**. Basically it is used when model needs external knowledge, so first we retrieve relevant context and then generate answer from that context.

**When it comes to what RAG is**
- So here the flow is, user asks question, system retrieves relevant chunks from knowledge source, and then LLM generates final response.
- This helps model give more grounded answer, instead of depending only on its pre-trained memory.

**When I would use RAG**
- I would use it when data is changing often, like internal documents, policies, product manuals, support knowledge, or enterprise data.
- In my kind of projects, if answer must come from company-specific content, then RAG is very useful because it improves relevance and reduces hallucination.

**When I would not use RAG**
- I would not use RAG for simple tasks where answer is already in model knowledge, like basic language generation or general reasoning.
- Also if data is very small and static, sometimes direct prompt is enough, so adding retrieval only increases complexity.

**Why it is useful**
- RAG gives better control because we can choose source documents, chunk size, and retrieval logic.
- So basically it is good when freshness, traceability, and domain-specific accuracy matter more than just generic generation.

Question:
- What is the difference between **WHERE** clause and **HAVING** clause?

Answer:
- Yes, basically **WHERE** is used to filter rows before grouping, and **HAVING** is used to filter after **GROUP BY**.

**When it comes to WHERE**
- **WHERE** works on individual rows, so it filters data before aggregation happens.
- I use it when I want to remove unwanted records early, like status, date, or category based filtering.

**Coming to HAVING**
- **HAVING** works on grouped result, so it is used after **GROUP BY** and aggregate functions like **COUNT**, **SUM**, **AVG**.
- So if I want only groups having count more than one, then I use **HAVING**.

**Here the main difference is**
- **WHERE** cannot directly use aggregate functions, but **HAVING** can.
- Example, `WHERE salary > 50000` is row level, but `HAVING COUNT(*) > 5` is group level.

**In my projects**
- In reporting and analytics type queries, I used **WHERE** to narrow raw records first, then **HAVING** to filter final grouped output.
- So that way query becomes cleaner and also more efficient.

Question:
- Do you know about window functions in SQL?

Answer:
- Yes, basically window functions are used when we want calculation on a set of rows, but without collapsing rows like **GROUP BY** does.

**When it comes to the main idea**
- A window function works on a "window" of rows and still keeps each row in result.
- So we can do things like running total, rank, row number, moving average, all these.

**Coming to the syntax**
- Normally we use **OVER()** with window function.
- Inside that we can use **PARTITION BY** to make groups and **ORDER BY** to define row order.

**For example**
- **ROW_NUMBER()** gives unique number to each row.
- **RANK()** and **DENSE_RANK()** are used when we want ranking based on some column.

**In simple words**
- So difference is, **GROUP BY** reduces rows, but window function keeps original rows and adds calculated column beside it.

Answer 20:
Question:
- Can you tell which window functions you know and define them?

Answer:
- Yes, I know the commonly used window functions like **ROW_NUMBER()**, **RANK()**, **DENSE_RANK()**, **LAG()**, **LEAD()**, and aggregate window functions like **SUM()** and **AVG()** with **OVER()**.

**When it comes to ranking functions**
- **ROW_NUMBER()** gives unique sequential number to each row, even if values are same.
- **RANK()** gives same rank for same values, but next rank will skip numbers.
- **DENSE_RANK()** also gives same rank for same values, but it will not skip next number.

**Coming to offset functions**
- **LAG()** helps to get previous row value.
- **LEAD()** helps to get next row value.
- These are useful when we compare current row with nearby rows.

**When it comes to aggregate window functions**
- **SUM() OVER()** gives running total or partition total.
- **AVG() OVER()** gives average over window without removing rows.
- So here we can do analysis row by row and still keep full result set.

**In simple words**
- So window functions are very useful for reporting, ranking, and trend analysis, because they give extra calculation without losing original rows.

- If data is huge, I also think about partitioning, caching, or rewriting query in simpler way.

- So basically, first identify bottleneck, then fix with index, query rewrite, and proper execution plan checking.

Answer 22:
Question:
- What is an index in SQL, and how does it improve performance?

Answer:
- An **index** is a database structure which helps to find rows faster, without scanning full table every time.

**When it comes to the purpose**
- It works like book index, so database can directly jump to required data.
- This is mainly useful for **WHERE**, **JOIN**, **ORDER BY**, and sometimes **GROUP BY** columns.

**How it improves performance**
- Without index, database may do full table scan.
- With index, it can use faster lookup path, so read query becomes quicker.
- So for large tables, response time improves a lot.

**One more thing**
- But index also has cost on **INSERT**, **UPDATE**, and **DELETE**, because index also needs maintenance.
- So normally we create index only on columns which are frequently searched or joined.

**In simple words**
- So index improves performance by reducing data scan and making row lookup faster, but we need to use it carefully.

Answer 23:
Question:
- What is the drawback of using an index in SQL?

Answer:
- Main drawback is it makes write operations slower and it also takes extra storage.

**When it comes to storage**
- Index needs additional space in database.
- If table is big and many indexes are there, storage usage increases.

**Coming to write performance**
- For **INSERT**, **UPDATE**, and **DELETE**, database has to update index also.
- So write operation becomes slower compared to table without index.

**One more thing**
- If too many indexes are created, maintenance cost increases.
- Sometimes optimizer may also choose wrong index if design is not proper, so query can still become slow.

**In simple words**
- So index is good for read, but drawback is extra storage and slower writes.

Answer 24:
Question:
- What is the **N+1 query problem**, and how do you fix it?

Answer:
- **N+1 problem** happens when one main query is fired first, and then for each record another query is fired again and again.

**When it comes to the problem**
- Suppose you fetch 1 list query, and then for 10 records, system runs 10 more queries.
- So total becomes 11 queries, that is why it is called **N+1**.
- This creates extra database calls and slows down application.

**How to fix it**
- I normally use **JOIN** when related data is needed together.
- In ORM side, we can use **eager loading** or proper prefetching, so data comes in fewer queries.
- Also I check query logs to identify repeated calls.

**In simple words**
- So basically, instead of querying inside loop, we fetch data in one shot or in fewer queries.

Answer:
- Basically, **useMemo** memoizes a **value**, and **useCallback** memoizes a **function**.

**When it comes to useMemo**
- I use **useMemo** when some calculation is costly and I want to avoid recalculating on every render.
- It returns the computed result, like filtered list, derived data, or any expensive value.

**Coming to useCallback**
- I use **useCallback** when I want same function reference to stay stable across renders.
- This is useful when passing function to child component, especially if child is using **React.memo**.

**Here the main difference is**
- **useMemo** gives me cached **result**.
- **useCallback** gives me cached **function**.

**In simple example**
- If I am doing `const total = useMemo(() => calculateTotal(items), [items])`, then total value is memoized.
- If I am doing `const handleClick = useCallback(() => doSomething(), [])`, then function reference is memoized.
