Question:
- How would you sort the numbers **5, 2, 3, 4, 1** without using built-in functions, and what flow and time complexity would you consider?

Answer:
- Yes, we can do it manually, basically by using a simple sorting logic like **bubble sort** or **selection sort**, and then I will explain the flow and time complexity.

**Coming to the flow**
- First I will take the array as **[5, 2, 3, 4, 1]** and compare elements one by one.
- If I use **bubble sort**, then I compare adjacent elements and swap if left side is bigger.
- So after first pass, biggest element goes to end, then second pass, next biggest goes to correct place, like that.

**If I explain with bubble sort**
- Compare **5 and 2**, swap, so array becomes **[2, 5, 3, 4, 1]**.
- Compare **5 and 3**, swap, so array becomes **[2, 3, 5, 4, 1]**.
- Compare **5 and 4**, swap, so array becomes **[2, 3, 4, 5, 1]**.
- Compare **5 and 1**, swap, so array becomes **[2, 3, 4, 1, 5]**.
- Then next pass continues until full array becomes sorted.

**Coming to time complexity**
- For **bubble sort**, worst case time complexity is **O(n²)**, because for each element we may compare with many other elements.
- Best case can be **O(n)** if array is already sorted and we use a flag to stop early.
- Space complexity is **O(1)** because sorting is done in-place.

**If interviewer asks for better option**
- I can also say **selection sort**, where I find minimum element and place it in correct position.
- That also has **O(n²)** time complexity, but number of swaps is less compared to bubble sort.
- So if simplicity is needed, bubble sort is easy to explain; if fewer swaps are needed, selection sort is better.

**In interview flow**
- I would say, first I choose a simple manual sorting method, then explain step by step swapping, and finally mention **time complexity** and **space complexity** clearly.

Answer 5:
Question:
- Can we sort it in **O(n)** instead of **O(n²)**, and if only first and last elements are unsorted, can we just swap them?

Answer:
- Yes, if the problem is only that **first and last elements** are misplaced, then one swap is enough and that becomes **O(1)** for that specific case.
- But if it is a general sorting problem, then no, we cannot sort any random array in **O(n)** using normal comparison-based sorting.

**When it comes to general sorting**
- For a normal unsorted array, comparison-based sorting has a lower bound of **O(n log n)**, so we cannot go to **O(n)** in general.
- So if interviewer asks about full sorting, I should say **bubble sort** or **selection sort** are **O(n²)**, and better algorithms like **merge sort** or **quick sort** are used for faster sorting.
- But those also are not **O(n)**, they are usually **O(n log n)**.

**Coming to your specific observation**

**How I would answer in interview**

**What is happening here**

**Why this is not swap**

- For that we need a temporary variable, otherwise one value will be lost.

**Correct swap flow**
- Store first element in temp.
- Put last element into first position.
- Put temp into last position.
- Then output becomes **[1, 2, 3, 4, 5]**.

**So the expected output**
- If only assignment is done, output will be **[1, 2, 3, 4, 1]**.
- If proper swap is done, output will be **[1, 2, 3, 4, 5]**.

Question:
- What is main difference between **encoder block** and **decoder block** in **Transformer**, and why we use them?

Answer:
- Yes, basically **encoder** is for understanding input, and **decoder** is for generating output.

**When it comes to encoder**
- Encoder takes full input sentence and builds contextual representation.
- It uses **self-attention** so each word can look at other words in same input.
- In encoder, all input tokens are available at same time, so it can learn full context.

**Coming to decoder**
- Decoder generates output token by token.
- It uses **masked self-attention**, so current token cannot see future tokens.
- It also uses **cross-attention** to attend encoder output, so generation is based on input context.

**Here the main difference is**
- Encoder is mainly for **representation learning**.
- Decoder is mainly for **sequence generation**.
- Encoder sees full input, decoder predicts next token step by step.

**Why we use them**
- We use encoder when task is like classification, embedding, understanding text.
- We use decoder when task is like translation, summarization, chatbot response generation.
- In many **LLM** and **RAG** type work, decoder side is very important because output is generated autoregressively.

**In my understanding**
- In **Transformer** architecture, encoder and decoder together help in sequence-to-sequence tasks.
- Encoder captures meaning, decoder converts that meaning into required output.

- So yes, encoder output is passed to decoder, but through attention mechanism, not as simple direct replacement.

**So the main point**
- Encoder output acts like context source.
- Decoder uses that context to produce final sequence step by step.

- So at time of predicting one word, model can only use previous words.

**How prediction happens**

**Why this works**

- During inference, model generates one token, then that token becomes input for next step.
- So it learns step by step, same way real generation happens.

**So simply**
- Masking does not tell the word directly.
- It only controls what decoder is allowed to see before predicting next word.

- But if you use a variable before assignment, with **var** you get **undefined**, and with **let/const** you get error.

Answer 59:
Question:
- What is event loop in JavaScript?

Answer:
- **Event loop** is the mechanism which manages execution of synchronous code, callbacks, and async tasks in JavaScript.

**When it comes to execution**
- JavaScript runs on single thread, so one task at a time only.
- First **call stack** handles normal synchronous code.
- Then async callbacks like **setTimeout**, promises, or API responses are handled through event loop.

**Coming to how it works**
- When call stack becomes empty, event loop checks **callback queue** and **microtask queue**.
- **Promise callbacks** go to microtask queue, so they get priority over normal timer callbacks.
- That is why promise output often comes before `setTimeout`.

**For example**
- If we have synchronous log, then promise, then timeout, output order is usually sync first, then promise, then timeout.
- So event loop keeps application responsive without blocking main thread.
